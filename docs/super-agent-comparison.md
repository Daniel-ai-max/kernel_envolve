# 研究流程与参考设计对比

研究循环由 agent 主导，框架只承担可复用的验证、资源与交付工作。先判断每项机制
能否减少实际成本，再决定是否保留；管理功能更多不代表优化效果更好。

长期任务、持久化执行意图和恢复机制借鉴 Super-agent 的公开原型。这里比较工程约束，
不把本地测试当成生产稳定性或优化效率的对照结果。

对照版本：[`deepseek-ai/dsh-superagent-prototype@8c32a9d`](https://github.com/deepseek-ai/dsh-superagent-prototype/tree/8c32a9dc5d72c033816c6a8110b37f40cf94fba4)。
其 [README](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/README.md)
明确区分公开研究原型、内部版本与文章中的未来设计。因此这里没有把文章里的完整
Watchdog、跨任务智能调度或自主组织能力当成已实现功能。

## 与裸 agent 的研究循环

kernel_envolve 不应限制 agent 的研究策略。它必须能执行同样的原生测试、微基准、
profiler 和候选批次，并允许从未晋升原型继续组合；quick 是可选筛选，full 用于交付。
单会话无需管理器或面板。多任务使用管理器时，一次 gpu-run 可以完成一批相关实验。

| 保留的机制 | 具体价值 | 成本放在哪里 |
|---|---|---|
| 固定原始基线、区分 best 与 candidate | 防止参照漂移，把局部信号误写为交付收益 | 首次接入确定契约，正式验收冻结与校验源码；局部实验记录差分 |
| 设备互斥、累计预算、进程清理 | 防止并发污染计时、重复占卡与残留进程 | 每个有界 GPU 作业统一管理，可批量候选；不逐参数注册任务 |
| 分层验证 | 用便宜实验淘汰错误方向，保留完整调用链和独立输入验收 | 探索只做本假设必需的检查；有信号才扩大范围 |
| 简短笔记与可恢复作业 | 减少重启后重复读仓库、重复提交已运行实验 | 复用同一任务，批次/交接保存增量记录；不重复归档全历史 |
| 实现、证据和 PR 绑定 | 防止提交的版本与通过验收的版本不同 | 交付与 PR 更新时校验，不阻塞候选探索 |
| 只读面板、后台历史审计 | 多任务状态可核对，研究报告与已验证收益分开 | 页面不扫源码；历史扫描在 GPU 队列繁忙时让路，观测时间保持真实 |

这些能力减少重复工程和可预防错误，不产生新的优化灵感。熟练裸 agent 也能自行实现；
框架的价值是复用可靠工具，省去反复搭建。如果单任务不需要调度，就不引入调度。

### 已发生的实验与结论

2026-11-10 的 DSA 六算子实验暴露了 bridge 空等约 105 分钟、整仓快照超过 90 秒、
一次 public quick 达到 715 秒的问题；正式 best 为 0/6。不能把框架功能或测试通过数
当作优于裸 agent 的证据。后续已支持原生命令批量探索、定向诊断、减少重复复制与
CPU 传输，并缩短 Skill；这些改动尚未完成同条件 GPU 效率对照。

同期裸 agent 的 self-KL 研究按 trace 选择机制，局部筛选后才做完整阶段与 CP8 模块验证，
取得了完整 dK 阶段约 1.19–1.21 倍、研究输入模块约 1.4–1.5% 的收益信号；原生 U/z
仍失败，尚不能正式交付。它同样维护独立 oracle、配对计时和研究笔记，“裸 agent”
不等于没有验证。两组基线、目标与预算不同，不能据此计算系统之间的速度比。

### 结构性约束与效果验收

代码层面应保证：局部批次无需正式 evaluator 或源码快照，面板请求只读已发布状态，
后台审计不成为 GPU 作业的前置条件，正式晋升仍验证完整证据。原生检查失败不能通过
放宽阈值、替换 oracle 或缩小声明范围解决。局部回归测试用于验证这些行为，不证明性能优势。

实际比较使用相同模型、算子、基线、硬件、输入范围与总预算，两组通过相同交付验收。
分别统计冷启动和稳态的候选到反馈耗时、有效假设验证数/卡时、首次可靠收益耗时、
完整调用链最终收益与最差退化，以及人工介入次数。计入准备、等待、失败、回传和归档，
保留全部尝试，独立确认输入不能交叉泄漏。提前固定判定口径并重复实验；不能仅挑最好一次。

有效实验指对一个明确机制得到可解释结论；证明候选错误或无收益也计入，重复提交、
基础设施故障和空轮不计入。模型 token/调用额度与墙钟额度也应相同。正式验收成本计入
首次可靠收益与总成本，不能通过一直留在局部测试阶段制造吞吐优势。

若新增管理成本没有被更少的重复实验、错误和交付成本抵消，就继续删除或移出热路径。
当前能确认的是流程可更轻、约束可复用，不能从设计直接推导必然更快或最终收益更高。

### 无 GPU 的命令反馈对照（2026-11-11）

主管原先在命令执行期间固定睡眠 200 毫秒再检查。改为限时等待子进程退出，长命令
仍按原频率检查取消、预算和父进程；完成的短命令可提前返回，不改变清理及计账。
同一台 macOS、同一 Python，CPU 命令每项计算一个 hash 并等待 20 毫秒。每组 12 对
交替 direct/managed，保留全部样本，
并反转版本顺序复测。两轮结果如下，单位为额外墙钟毫秒：

| 执行方式 | 原主管 | 修改后 |
|---|---:|---:|
| 单个 CPU 测试项，managed − direct 配对中位数 | 227–234 | 60–62 |
| 8 项一批，managed − direct 配对中位数 | 260–264 | 55–56 |
| 8 项一批，摊到每项 | 32.5–33.0 | 6.9–7.0 |

加入 10,000 条已结束作业记录后，新版单项/批次额外耗时约 60/55 毫秒，本样本未见
明显退化。管理仍有成本：单会话可直接运行原生命令，需资源保护时批量执行相关实验。
这不测量 GPU 探测、完整 evaluator 或模型研究效果，也不替代同条件算子搜索对照。
复现脚本见 [benchmark_manager_feedback.py](../tools/benchmark_manager_feedback.py)，
全部原始样本与源码指纹见 [manager_feedback.json](../audit/manager_feedback.json)。

### 多卡准入开销（待 GPU 验证）

设备空闲检查原先对每张卡分别查询 UUID 和计算进程，8 卡每个检查点启动 16 次
`nvidia-smi`。现在健康路径对整个设备组查询两次，准入和清理各自读取实时状态，
不缓存空闲结果；驱动输出顺序不改变 rank 顺序。任一查询失败仍拒绝放行，并逐卡
诊断，后续诊断成功不能覆盖原失败。锁、预算、清理及正式评测不变。

无卡回归覆盖设备缺失/重复/额外 UUID、占用、驱动错误、超时和生命周期；它仅证明
模拟驱动响应下的控制逻辑。实际 B300 驱动对多 UUID 查询的支持及反馈耗时仍须实测，
该变更应在完成这项 GPU 检查后合入，不把调用次数减少换算成实测加速。

## 能力映射

| 关注点 | Super-agent 公开原型 | 本实现 |
|---|---|---|
| 长期任务与执行分离 | Ticket / Assignment / Executor Session | task / agent round / 可配置 argv 适配器；每轮结束保存 checkpoint，算子任务继续 |
| 提交后执行 | Engine 在事务中记录 Effects，提交后由适配器执行 | SQLite 事务预留名额并保存 job，提交后启动独立主管；不靠内存任务列表 |
| 持久化 | SQLite WAL / FULL、领域记录与待执行效果 | SQLite WAL / FULL；任务、进程身份、队列、累计用量、报告、事件与证据索引 |
| 重启恢复 | 保留 Session 等状态，记录中断的 Assignment，并带恢复说明继续 | 协调器重启不终止存活主管；身份匹配才接管；失联时先清理子进程、核对锁，必要时隔离资源 |
| 执行并发 | Executor 槽位与队列 | 每资源 1–2 个 Agent 会话；GPU 作业独立 FIFO；同一用户下按物理 UUID 加宿主锁 |
| 失败与暂停 | 失败持久化、有限重试、退避、人工继续 | 累计 wall/GPU 额度、轮次超时、失败退避及带诊断证据的后续轮次；用户暂停持久化取消意图 |
| 进展呈现 | Ticket 状态、需要人处理的问题、系统问题 | 总览、任务详情、资源队列；显示真实阶段、证据问题与资源阻塞，不伪造完成百分比 |
| 结果可信度 | Executor Report 与外部系统状态 | 研究报告与 evaluator 事实分开；只有完整验证且通过晋升链的 best 展示收益 |
| 基线溯源 | 非算子专项能力 | 固定仓库/版本/入口、实现提出日期与来源、冻结日期、硬件、评测契约 |
| 外部事件与授权 | Sources、Threads、Mandates、输入投递和消息 Outbox | 固定任务和明确资源配置；不引入消息连接器、提醒、隐式任务发现与授权推断 |
| 模型运行时 | DeepSeek Harness 接口 | 不新增推理循环；适配器消费 stdin 恢复提示，写结构化报告，可自行复用宿主 Session |

## 为算子优化增加的约束

同一 GPU 上可以有两个 Agent 同时分析、改代码，但正确性检查、编译、benchmark 和
profiler 都必须经过 `manage gpu-run`。GPU 作业结束、拥有者进程身份与设备锁是释放
依据；心跳过期只代表需要检查。独立进程组的 evaluator 子进程也登记身份并继承锁，
覆盖尚未创建 CUDA context 的导入/编译阶段。无法确认清理完成时停止资源复用。

原始 baseline 固定。当前候选、已验证 best 和 Agent 报告的已集成版本分别存储；每次
晋升记录前一个 best、结果 hash 和晋升时间，面板只认可从当前 best 可达且经过校验的
链。收据删除、源码篡改、契约变化、结果目录丢失都会使对应证据失效。旧记录没有
晋升时间时保持未知；历史 GPU 用量只是索引时的观测值，不冒充晋升当时的精确消耗。

界面展示 baseline、已验证收益、最近实现 PR 及更新时间、累计卡时和研究进展；
详情保留逐场景延迟与历史，研究报告不替代验收结果。
没有常驻教程、免责声明或消息提醒。收益是单算子固定契约下的结果，不推导框架收益。

实现集中在 [manager](../src/kernel_envolve/manager/)：`store` 负责事务、`service`
负责协调、`worker`/`gpu`/`process` 负责生命周期和资源、`evidence` 负责结果校验、
`views`/`web` 负责查询和本机面板。复用标准库 SQLite/HTTP，不增加运行时依赖。

## 验证与运行范围

行为验证见 [管理层测试](../tests/test_manager.py)、[原生证据测试](../tests/test_manager_native.py)
和 [指纹检查测试](../tests/test_manager_fingerprint.py)。配置与运行方式见
[管理文档](optimization-manager.md)。当前测试状态以对应提交的 CI 为准。

管理器面向单主机、同一用户的受信工作流，不提供 OS 沙箱。支持单 GPU 和同机多 GPU
资源组；跨主机调度由外部平台负责。源码、硬件和评测契约变化不能继承旧收益。
后台审计保留原观测时间，忙时可延后；正式晋升始终重新验证。
