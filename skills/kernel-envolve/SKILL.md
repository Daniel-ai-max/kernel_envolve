# Kernel Envolve

## 目标

在用户指定的算子、环境和预算内，找到正确、适配实际输入范围且有实测收益的实现。研究由 agent 自主选择机制、实验粒度和验证时机；管理与归档服务于研究，不要求每个尝试经过固定流程。持续优化任务沿用已有授权和额度；保存候选、晋升或更新 PR 后继续研究，不将单次会话结束当作任务结束。普通任务不自动扩展为持续运行。

## 正确性与交付约束

- 区分独立数值 oracle、固定原始 baseline、已验证 best 和探索 candidate。baseline parity 不等于独立数值合格。保留既有精度/bitwise、相关梯度和状态语义门槛，不豁免历史 FAIL；历史整链失败不阻止经独立验证的未受影响子任务研究，但仍阻止相关交付。源码、契约和环境匹配的资格证据可复用。
- 交付验证覆盖真实调用链与生产输入范围，包括尺寸、各输入布局、dispatch 边界和 fallback；局部 kernel 收益不外推训练收益。性能比较保持等值输入与状态、独占设备、预热和交替计时，计入实际准备、转换与同步成本；eager/Graph及通信链路分别验证。详见[原生评测](../../docs/native-harness.md)或[独立任务评测](../../docs/generic-evaluator.md#输入覆盖与交付)。
- 有收益信号再进入 full 与未参与选择的输入确认；quick、局部实验和成功退出码都不更新 best。已见确认输入转为回归，不能重复抽样直到通过。内部任务使用 `native-confirm` / `native-promote`，独立任务用独立验证任务确认后 `promote`；具体门禁见[确认规则](../../docs/native-harness.md#独立确认)与[结果使用](../../docs/generic-evaluator.md#结果使用)。
- 正式结果通过哈希绑定冻结源码、输入、环境与评测契约，交付实现及 helper 必须与验证快照一致，行为变化后重验受影响部分。保存失败和原始证据，不能以摘要代替完整正式归档。逐场景报告延迟与最差退化，按真实任务权重汇总；不得用测试数量、局部加速或管理功能宣称整体优势。
- 用户停止、累计预算和终态有效，换轮不重置额度、不复活已停止任务。批次交接或资源释放前持久化新增证据，核对所有所属作业、后代进程与 GPU 清理；管理任务还须保存一致性状态。不要回收唯一证据副本。恢复和预算细节见[管理层](../../docs/optimization-manager.md#操作与恢复)。

确认正确性、实际调用链收益和独立输入后，维护本任务的实现 PR，探索候选与已验证交付分开。沿用项目模板，用中文说明变化、版本、计时范围、场景收益/退化和复现证据；内部项目还须核对实际 core/Megatron 接线与 pin。交付边界的 `manage sync-pr` 见[管理接口](../../docs/optimization-manager.md#agent-适配接口)。

## 工具用法

使用 `kernel-envolve update` 返回的 Skill 与 `executable` 绝对路径；已固定的实验轮次沿用其版本，full/confirm/promote 之间不升级。更新、离线和禁用行为见[更新规则](../../docs/auto-update.md)。接续时核对已有源码、记录和在途作业，避免重复提交；不要求为每个实验更新工具、注册任务或另开管理轮次。

可直接执行原生测试、编译检查、profiler、微基准或批量实验脚本。需要 evaluator 时，原生任务用 `native-evaluate`，独立任务用 `evaluate`；quick筛选与`--check-only`故障定位均按需使用，不作为每次探索的前置步骤。配置和参数见[原生快速迭代](../../docs/native-harness.md#快速迭代)、[独立评测模式](../../docs/generic-evaluator.md#评测模式)；同进程配对可用[research工具](../../docs/native-harness.md#轻量研究工具)。

已管理任务的所有 GPU 命令通过下面的入口执行，包含访问 GPU 的编译和局部检查。一次有界命令可批量测试相关候选；不得嵌套或遗留后台 GPU 进程。预计时长之外还须在原额度内预留启动、清理及证据保存时间。

```sh
kernel-envolve manage gpu-run --expected-seconds <预计秒数> -- <原生实验命令>
```

前台宿主使用 `manage bridge-request --file request.json` 提交原生命令。下一请求可选携带 `analysis={request,receipt_sha256,outcome,round?,next_action?}`，将对已有结果的真实分析一并保存；无需独立 consume，也不要求每次写分析。独立 consume 仅供旧客户端兼容。查询已有请求不带请求文件或 analysis，只读返回状态/结果，不生成分析或提交新工作。同一请求 ID 不重复执行；响应不确定时查询原 ID，不换 ID 重派。等待、恢复和字段定义见[前台 bridge](../../docs/optimization-manager.md#前台宿主接续)。

有独立工作可做时使用 `--wait-seconds 0` 先返回，需要结果时有界等待；按决策需要核对日志与产物，截断 stdout 不代表全部实验结果。CPU 分析不占 GPU 队列；CUDA 故障后不要继续使用故障进程。单会话研究不要求先部署管理器或面板。预算内自动续接必须连接真实模型宿主，配置见[宿主接续](../../docs/optimization-manager.md#预算内自动接续)；bridge 在线不代表模型在研究。

## 研究建议

优先用能否定机制的便宜实验筛选方向，再扩大到完整阶段和调用链；计算组织、数据移动、融合、反向和布局通常比机械参数遍历更值得检查。代表输入与可能退化的边界都可用于局部验证；相关参数可在一次作业内成批测量，保留各候选结果。按需从慢场景、退化、完整调用链瓶颈、机制组合或泛化中选择下一个能获得新信息的问题，复用已否定方案的证据。有信号才支付 full 与独立确认成本，inconclusive 不等于更慢，也不应触发无依据的反复抽样。

复用环境、固定输入和按源码/配置区分的编译缓存；硬件能力与参考实现按需查[硬件入口](references/hardware.md)。原始运行记录能还原源码、参数、命令、退出码与结果即可；已有记录不再逐次抄写到 `notes.md`。需要交接时留下简短结论和未完成工作，不规定逐实验模板或固定研究顺序。
